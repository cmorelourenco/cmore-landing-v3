# Documents: data and rules

How the Documents area decides what a company is asked for. The prototype runs on exactly these files, so the backend can use them as they are.

| File | What it is | Who changes it |
| --- | --- | --- |
| `Document_List_v2.xlsx` | The catalog: every document type, its fields, checks, statuses and profile forms | Product |
| `data/document-catalog.json` | The catalog as data, generated by `tools/catalog2js.py` | Nobody by hand: regenerate it |
| `js/doc-rules.js` | Which documents a company sees, from the catalog and its profile | Developers, when a new condition appears |

Adding a document, renaming one, changing its requirement or moving it between EU and US means editing the workbook and regenerating. No code changes.

For now the prototype works for an EU company, so documents only for US companies (Scope `US`) are left out when the catalog is generated; `EU + US` documents stay. `tools/catalog2js.py` also reads a row that repeats the code above it with Scope, Requirement and Level empty as a variant of that document: CO-21 is ISO 9001, and ISO 14001, ISO 45001, ISO 27001 and Others become CO-21.1 to CO-21.4, with the rest of CO-21's details and fields.

## The catalog (`document-catalog.json`)

- `docs[]`: one entry per document type.
  - `code`: stable ID (`CO-01`, `WK-11`, `UN-05`…). It never changes once in production.
  - `category`: `company`, `workers`, `equipment`, `products` or `sites`.
  - `section`, `name`, `description`: `{ en, pt }`.
  - `scope`: `["EU"]`, `["US"]` or `["EU","US"]` (workbook column J).
  - `sectors`: `"any"` or `["construction"]` (column K: Transversal / Construction specific).
  - `requirement`: `mandatory`, `if_applicable`, `on_request` or `optional`.
  - `condition`: a condition key or `null` (see below). `appliesWhen` keeps the workbook's wording.
  - `level`: `company`, `all_workers`, `per_worker`, `per_equipment`, `per_product` or `site`.
  - `hasIssueDate`, `expiryRule`, `renewal`, `checks`, `sharing` (`standard`, `restricted`, `requesting_client`), `phase`, `legalBasis`.
  - `titles`, `usuallyIssuedBy`, `recognitionCues`, `confusedWith`: classification cues for Alma.
  - `fields[]`: what Alma extracts, as `{ name, type, requiredToSave, extractedByAlma, editableByUser, visibleToClients }`.
- `conditions[]`: every condition key, as `{ key, subject, kind, question, drivenBy }`.
- `checks[]`: V1–V8, the checks Alma runs on every document.
- `statuses[]`: document, contractor and site statuses, with their rules.
- `profiles`: the fields of the Company, Worker, Equipment, Product and Site forms.
- `labels`: display names for the enums above.

## The rules (`js/doc-rules.js`)

```js
const R = require('./js/doc-rules.js');          // or window.DocRules in a page
const catalog = require('./data/document-catalog.json');
const profile = { country: 'PT', sector: 'construction', entityType: 'company',
                  employees: 24, services: ['construction_work'], equipmentCount: 12, usClients: false };

R.documentsFor(catalog, profile);   // [{ doc, shown: true, ask }], the documents this company is asked for
R.evaluate(catalog, profile);       // every document, with { shown, why } — why: phase, scope, sector, area, condition
R.subjectsFor(doc, workers, profile); // the workers, machines or products a per-record document covers
```

A document reaches a company when all of these are true:

1. **Phase**: it is live (`MVP` by default; pass `{ phases: ['MVP', 'Phase 2'] }` to include more).
2. **Scope**: it covers the company's region. The region comes from the country (`US`, or `EU` for EU/EEA countries).
3. **Sector**: it is for any sector, or `sectors` includes the company's sector.
4. **Area**: Workers needs employees; Equipment needs at least one equipment record; Products needs `material_supply` among the service types. Sites stays hidden until it is reworked.
5. **Condition**: if the document has one, it isn't false for this company.

There are two kinds of condition:

- **fact**: read from data the platform already has, either the company profile (`has_employees`, `self_employed`, `foreign_posting`, `construction_work`, `own_equipment`, `non_us_for_us_clients`) or each worker, machine or product (`worker.non_eu`, `equipment.built_before_1995`, `product.hazardous`…). If it's false, the document isn't asked for.
- **answer**: only the company knows (`transports_goods`, `produces_waste`, `imports_cbam`…). The document is asked for (`ask: true`) until the company marks it Not applicable with a reason. That is the catalog's "Mandatory if applicable" rule.

Per-record documents (`per_worker`, `per_equipment`, `per_product`) are asked for once per record that `subjectsFor` returns. The status of the row that sums them up is the worst of theirs.

## What isn't decided by the rules

These come from each company's own data, not the catalog:

- **Status**: Missing, Valid, Expiring… from what was uploaded and Alma's checks (the Statuses sheet).
- **On client request**: required only once a client asks for it. Until then the prototype shows it as *Not requested* and leaves it out of the totals.
- **Optional**: never required. The prototype shows it as *Not uploaded* until there is one, and it doesn't count towards the totals.

## Adding a condition

1. Add the key to the workbook's `Conditions` sheet and to the document's `Condition key` column, or to `CONDITIONS` / `APPLIES_WHEN` in `tools/catalog2js.py`.
2. If it's a fact, add how to read it to `FACTS` in `js/doc-rules.js`. An answer needs no code.
3. Regenerate. The generator refuses a key it doesn't know.
